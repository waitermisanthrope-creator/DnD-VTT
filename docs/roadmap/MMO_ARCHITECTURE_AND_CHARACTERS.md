# MMORPG: техническая архитектура, персонажи и живой мир

**Статус:** [НЕ ВЫПОЛНЕНО] / WAIT_TEAM. Документ-предложение к будущему kick-off; не использовать как разрешение на разработку MMO. Главный документ — [генеральный план](DUAL_MODE_MMO_MASTER_PLAN.md).

## 1. Одна платформа, две системы

```text
Unity Android / Windows
  ├── PlatformCore: аккаунт, настройки, кроссплей, логин, обновления, UI
  ├── Content/WorkshopCore: ID, каталог, версии, зависимости, графика, права
  ├── CharacterDefinitions: расовые/классовые/предметные определения
  ├── VttRuntime: 5e-листы, пошаговые действия, сессии, мастер кампании
  │     └── локальные + VTT-облачные персонажи/кампании
  └── MmoRuntime: real-time бой, зоны мира, AI, мастера, экономика
        └── authoritative MMO backend + отдельные серверные персонажи
```

Общий C# код и дата-контракты допустимы, **но не единая мутируемая сущность персонажа**. Клиентский VTT-сейв нельзя считать MMO-профилем. Действия UI — команды к соответствующему runtime, а не напрямую общие переменные HP/XP/инвентаря. Для обеих платформ применяются одни контракты и контроль версий; следить за Android low-end.

### Матрица игрового режима

| Свойство | VTT | MMO |
|---|---|---|
| Партийность | 1–15 игроков + мастер | Цель: 100+ игроков в общем мире, около 10 мастеров |
| Время | Пошаговая инициатива | Реальное время и серверная симуляция |
| Статистика | D&D по правилам кампании | Адаптация D&D к cooldown/cast/reaction/periodic tick |
| Мир | Отдельные карты/кампании | Постоянный мир, регионы/чанки |
| Авторитет | Ведущий кампании/её контракт, возможен локальный режим | Только MMO-сервер |
| Персонажи | Независимые сохранения | Независимые записи на сервере |
| Деньги | Правила кампании и отдельная VTT-модель доступа | Серверная валюта + платный магазин |
| Мастер | Ведёт конкретную кампанию | Оперирует назначенными мировыми событиями, общим каноном |

## 2. Асимметричная миграция персонажей — БЕЗ ИСКЛЮЧЕНИЙ

**VTT → MMO: категорический запрет.** Не разрешать через скрытые API, импорт локальных файлов, общие UUID, синхронизацию, обход через мастерскую или передачу денег/предметов.

**MMO → VTT: допускается экспорт отдельной копии, а НЕ миграция оригинала.**
1. По авторизованному запросу MMO-сервер выдаёт проверенный снимок персонажа (идентификатор, уровень, класс, способности, экипировка, допустимые метаданные и версия правил). Не брать неподписанный файл от клиента за эталон.
2. `MmoToVttConverter` с версией контракта конвертирует snapshot в новую VTT-заготовку; сохраняет ссылку на происхождение только как справку (`sourceMmoCharacterId`) и новый независимый `characterId`.
3. Неподдерживаемые real-time умения становятся описанием, ручным вариантом или явно требуют дополнительный пакет/решение мастера; валюта и несопоставимые предметы не переносятся автоматически.
4. Мастер конкретной кампании утверждает/отклоняет и вправе адаптировать героя в пределах VTT. Несогласие не затрагивает MMO-оригинал.
5. Любые изменения VTT-копии **никогда** не возвращаются в MMO. Повторный экспорт образует новую копию или явно выбранную новую VTT-версию, но не двустороннюю синхронизацию.
6. Платные права MMO не дают автоматически права самостоятельно создавать VTT-материалы без соответствующей лицензии. Экспорт не должен становиться обходом entitlement.
7. Тесты: VTT-клиент подменяет XP/Gold/способности — MMO неизменен; удаление VTT-копии — MMO сохранён; server bans/возвраты/блокировка модов — без потери локальных сейвов.

## 3. Реальное время + дух D&D

Классы, расы, умения, предметы, заклинания, типы урона, характеристики и проверки — общий **контентный словарь**, но не обязательно общий исполнитель. Чистый мод с `description` в JSON не эквивалентен реализованному серверному действию.

| Настольная механика | MMO-аналог для исследования |
|---|---|
| Инициатива и ходы | Real-time очередь действий, speed/animation lock/cast |
| Действие/бонусное/реакция | Разные окна, cooldown и лимиты |
| Попадание/КД | Серверная проверка/бросок по изменённым правилам |
| Ячейки заклинаний | Ограниченный ресурс и регенерация/отдых |
| Концентрация | Поддержание эффекта и серверное прерывание |
| Состояния и AoE | Серверные эффекты и пределы на цели/тик |
| Лечение/сопротивления | Серверные формулы с балансом PvE/PvP |

Правила нельзя менять в VTT ради MMO. Баланс должен учитывать 100 игроков, реальный тайминг и P2W. Сервер считает попадания, кулдауны, дальность, контроль, расход инвентаря и награды. Клиент предсказывает только визуальное движение/отклик, сервер валидирует конечное состояние.

Тестировать слабые Android-устройства, ping/jitter, дуэли, массовые битвы с фамильярами, AOE, NPC и 10 ведущими. **100 игроков в мире ≠ 100 одновременных кастующих в одном месте.**

## 4. Серверные модули (логическая схема)

```text
[Unity Mobile/Windows]
        |
[API/Login + Token validation] ─── [Account/Supabase identity]
        |
[Gateway / Session Router]
        ├─ [MMO Characters + Inventory + Economy DB]
        ├─ [World State / Canon + Event Journal]
        ├─ [Zone A] [Zone B] [Zone C]  ← Authority over AI/movement/combat
        ├─ [GM/Scenario Operations]
        ├─ [Content Registry + CDN + Entitlements]
        └─ [Orders / Billing / Refunds / Audit]
                  └─ [Monitoring, deployment, backups]
```

**Supabase** может быть частью системы логина и метаданных, но не является готовым real-time MMO-сервером. Авторитетному серверу необходимы постоянные игровые процессы/хостинг, anti-dupe транзакции, трассировка сетевых команд и управление зонами. Не помещать service-role ключи или GitHub/App secrets в APK.

**Чанки** — единицы хранения/стриминга окружения, с целочисленными координатами (+ и -). **Зоны** — единицы серверного авторитета, могут содержать много чанков. Server handoff пересылает игрока атомарно, не допускает двух активных owners одного героя, двойного начисления наград и дюпов. AOI уменьшает сетевую рассылку объектов, не отменяет подгрузку графики.

**Networking:** оценить Unity Netcode for Entities, Photon Fusion и другие варианты только по прототипам на Android/Windows с данными о лицензировании, количестве клиентов на зону, p95 latency, восстановлении и стоимости эксплуатации. Выбор пока **не принят**.

## 5. Система десяти мастеров и единый сюжет

Живые мастера могут управлять персонажами NPC, событиями, погодой, спавнами, квестами, фракциями, региональными изменениями, заданиями для игроков — но **строго через серверные команды** и пределы выданных прав, а не напрямую редактируя БД.

**Общая доска мировых событий:** сюжетная арка → региональные сценарии → запланированные триггеры → опубликованные канонические результаты → уведомление всех задействованных мастеров. Изменение мира хранит ID события, автора, время, версию, сущности, регион, последствия и, где возможно, обратимую компенсационную операцию. Два конфликтующих изменения должны приводить к разрешению конфликта, а не к «последний записал — тот прав».

Пример: некроманты начинают нашествие. Мастер королевства получает приказ о мобилизации, мастер леса фиксирует заражение фауны, мастер шахт — связь с артефактом. Решения игроков отражаются в карте фракций и доступных заданиях. Резолюция глобального сюжета не может быть куплена нажатием одной P2W-кнопки.

**Не путать канон с журналом модераторов.** Каноническая история и ревизии мира нужны долго; историческая схема модерации с 24-часовой видимостью логов не подходит для хранения сюжета.

## 6. Два вида редактора

**VTT DM:** подготовка карт, комнат, миниатюр, классических сессий и пошагового боя.

**MMO World Master:** работа внутри полномочий сервера над живым регионом, NPC, событиями и публикуемым миром; сценарии проходят версионирование, конфликтный контроль, безопасную активацию/откат, возможность взаимодействия нескольких мастеров.

**Переиспользование контента:** можно создавать в VTT карту/подземелье/диалоги и адаптировать в MMO через отдельный валидатор/конвертер. **Это перенос контента, а не персонажей VTT.** Произвольные правила/скрипты/объекты не попадают автоматически в сервер MMO.

## 7. Приёмка архитектурного прототипа после старта

- Один аккаунт; отдельный VTT- и MMO-персонаж без конфликтов ID, XP и денег.
- Android и Windows подключаются к одному серверному миру, смена зоны с переподключением/восстановлением не дублирует инвентарь.
- Сервер не принимает изменённые клиентом HP/деньги/удар/позицию за факт.
- Два мастера публикуют события одного сюжетного объекта — конфликт разрешён корректно и журнал сохранился.
- MMO → VTT создаёт новую копию; VTT → MMO отвергнут на всех API; сохранения исходного персонажа не повреждены.
- Отдельный тест 5–10 игроков, затем разные уровни нагрузки. Результаты фиксировать реальными измерениями.
