# Content Streaming Manager — подгрузка миров и VTT-карт без установки всей мастерской

**Статус:** [НЕ ВЫПОЛНЕНО] / WAIT_TEAM. Архитектурное предложение для будущего MMORPG и обычных VTT-сессий. Не реализовывать до отдельной команды на старт. Основание: [генеральный план](DUAL_MODE_MMO_MASTER_PLAN.md).

## 1. Проблема, которую обязан решить движок

Игрок установил базовое приложение Android/Windows, **ничего не скачал в мастерской**, вошёл в онлайн-мир и отправился в болота/горы/пещеры Лорда Енота. В этих регионах применяются неизвестные ему текстуры, модели, материалы, анимации и звуки. **Нельзя требовать предварительно скачать гигабайты ресурсов или посещать мастерскую вручную.**

Также обычный игрок присоединяется к VTT-сессии мастера, где используются платные или бесплатные пакеты карты, которыми он **лично не владеет**. Игрок должен получить необходимые игровые данные на время партии в рамках проверенных прав, без автоматической покупки.

**Решение:** доверенный серверный manifest зависимостей + менеджер потоковой загрузки + встроенные облегчённые ресурсы + два независимых типа дискового хранения и RAM/GPU residency.

## 2. Четыре пространства хранения

| Слой | Что хранит | Очистка |
|---|---|---|
| `Built-in Core` | Базовые персонажи-заглушки, коллизии, упрощённые деревья/камни/стены, универсальные материалы, критические UI/эффекты внутри APK/EXE | Не удаляется отдельно от приложения |
| `Installed/Pinned Workshop` | Моды, которые пользователь **сам** установил/закрепил | Только вручную или по явно согласованному действию |
| `Ephemeral Disk Cache` | Региональные/сессионные пакеты, подгруженные автоматически | По LRU/TTLs/лимиту, только если не используются |
| `RAM/GPU Active Assets` | Текстуры/меши/материалы и AssetBundle, активные в текущей сцене | Выгружаются при исчезновении ссылок/выходе из интересующей зоны |

**Удаление файла с диска ≠ выгрузка из RAM/GPU.** Не удалять активные файлы при стриминге/распаковке. Не выбрасывать по LRU пользовательские pinned-дополнения, персонажей, сейвы или ручные скачивания.

## 3. Цикл вхождения в новую локацию

1. `Region Resolver` получает от сервера/мастера *не список чужих произвольных URL*, а **доверенный manifest** ресурса/версии/платформы/размера/SHA-256/совместимости/прав.
2. `Dependency Planner` строит граф обязательных и необязательных зависимостей. Граф ацикличен; ошибки отчётливы. **Critical:** коллизии/навигация/важные механики. **Optional:** высокодетализированные материалы, вариации мешей, декоративный звук.
3. `Asset Locator` сначала ищет байты в pinned-пакетах и временном диске по уникальному ключу `(id, version, platform, sha256)`. **Не скачивать** повторно одно и то же дерево для нескольких зон.
4. `Budget Guard` проверяет свободное место, лимит дискового кэша, настройки Wi-Fi/мобильных данных, батарею/слабое устройство и реальный требуемый размер; показывает ожидаемый объём.
5. `Downloader` ограниченно и атомарно докачивает только недостающие пакеты, проверяет допустимый адрес/подпись каталога/хеш/размер/совместимость и активирует ресурс **после полной проверки**. Контентный хеш доказывает целостность, но сам по себе не авторство.
6. `Scene Presenter` показывает упрощённую сцену, пока грузится optional-графика; затем подставляет высококачественные ассеты без дублирования коллизий/объектов.
7. `Region Prefetch` учитывает положение/направление/скорость игрока, заранее загружает соседние чанки; отменяет ненужные заявки. В зависимости от профиля допускается вообще не предзагружать.
8. `Refcount/Cache Evictor` после ухода из зоны освобождает неиспользуемую RAM/GPU и удаляет временные файлы по лимиту/возрасту. Не трогает используемое и pinned.
9. При потере интернета/нехватке места/ошибке SHA — понятное сообщение и безопасный fallback. Никогда не утверждать, что критическая сцена полностью доступна, если нет критических данных.

Пример из беседы: условное болото имеет 12 МБ текстур, 18 МБ деревьев, 15 МБ существ, 4 МБ звука и 3 МБ эффектов — всего **52 МБ условно**, но ближайший участок может потребовать только часть. Это **иллюстрация**, не реальная оценка контента.

## 4. Качество изображения и пользовательский контроль

Предлагаемые режимы:
- **Экономия:** только необходимый минимум, облегчённая геометрия, низкий LOD, минимальная предзагрузка, агрессивная очистка.
- **Сбалансированный:** умеренная предзагрузка и разрешение текстур, средний лимит кэша.
- **Максимальное качество:** высокие LOD, большая текстурная детализация, разумная предзагрузка.
- **Только базовые ресурсы / запрет скачивания тяжёлого контента:** встроенный fallback, никаких крупных optional-asset packs.

Индивидуальные настройки: **Wi-Fi only**, разрешение мобильной сети, потолок скачанного трафика, максимальный временный диск, очистка после выхода, разрешение предзагрузки, оповещение перед крупными пакетами, pin понравившихся ассетов. Кроссплатформенная синхронизация настроек не должна переносить 8 ГБ дискового лимита Windows на слабый Android.

**Предварительные примеры лимитов временного дискового кэша — НЕ утверждены:**

| Режим | Android | Windows |
|---|---:|---:|
| Экономия | 128 МБ | 512 МБ |
| Сбалансированный | 512 МБ | 2 ГБ |
| Максимум | 2 ГБ | 8 ГБ |

Числа не относятся к RAM и обязаны пройти мобильное профилирование. Система учитывает запас свободного места, критический предел ОС и защищённые файлы.

**Невозможно показать уникальную модель без её данных.** Если пользователь запретил любое получение нового контента, доступны только встроенные ассеты или ресурсы, уже локально сохранённые. Для обязательной графики/логики, которую нельзя корректно заменить, клиент должен запросить разрешение на минимальную загрузку либо объяснить, почему этот участок пока недоступен.

## 5. Чанки, AOI, LOD и общие ассеты

Разделить геометрию на координатные чанки (включая отрицательные координаты), каждый из которых знает список зависимостей и допустимые LOD. В текущем `01_plansforproject.md` уже есть **не выполненная** цель по чанкам. Пример размера 128 × 128 м — только гипотеза: выбрать после измерений.

Клиент держит текущие и ближайшие чанки, но может показывать далёкие горы с низким LOD. **AOI серверной сетевой синхронизации** и область подгрузки ассетов — близкие, но разные механизмы; не надо пересылать всей карте сведения обо всех NPC, а визуальным ресурсам не нужны отдельные копии в каждой области.

**Важно для PvP:** low-quality игрок не должен видеть противника через отсутствующие стены/кусты, если high-quality игрок не видит. Серверная коллизия/видимость одинаковы для всех; fallback-геометрия отображает реальные непроходимые объекты/укрытия. Смена LOD не меняет размер хитбоксов, навигацию или боевые правила.

## 6. Мастерская: постоянные моды и сессионные материалы

Текущая система использует:
- `DnD-VTT-Content/catalog/v3/index.json` и `DnD-VTT-Assets/catalog/v4/index.json`;
- `unity/Assets/Vtt/Runtime/WorkshopStore.cs` — проверка manifest, размеры, SHA-256, атомарная установка и Remove;
- `WorkshopRuntime.cs` — декларативные материалы, verified AssetBundles, освобождение части загруженного;
- `LegacySessionPanel.ContentManager.cs` — каталог/ручная загрузка/удаление.

**На дату плана нет:** автоматического streaming-а регионов, LRU disk cache, контролируемого разделения ephemeral/pinned, гарантированных fallback для всех материалов, полноценной системы связанного с кампанией session entitlement. Эти пункты нельзя выдавать за реализованные.

### VTT-случай: мастер приобрёл карту
1. Сервер проверяет покупку/право мастера, активную VTT-сессию и участие конкретного гостя.
2. Сервер выдаёт **временное право на необходимые игровые ресурсы сессии**, не право владения пакетом и не право создавать/публиковать платную карту.
3. Клиент скачивает необходимые данные с проверкой размера/подписи/хеша и кэширует. По завершении сессии доступ к следующей выдаче заканчивается; уже сохранённые данные не служат лицензией.
4. Сейвы и ссылки на карту не удаляются из-за истечения временного права. Отсутствующий платный ассет корректно помечается как недоступный.
5. Приобретение платного MMO-меча не переносит право собственности на одноимённый VTT-пакет без отдельной политики.

## 7. Раздача и форматы

**Будущая целевая комбинация:** Content manifest + Unity Addressables + проверенные AssetBundles (отдельно Android ARM64 / Windows x64) + CDN/object storage для большого онлайна. Точный Unity/Addressables SDK зависит от версии проекта и проверок. JSON-каталоги и GitHub Releases остаются начальным workflow разработки/публикации и **не обязаны оставаться массовым MMO-CDN**.

Крупные наборы группировать по совместному использованию, платформе, LOD и вероятности повторного скачивания, а не «весь континент в одном bundle». Проверять licence/provenance, asset source и размер. Не разрешать произвольные C#/DLL/JS-сценарии из пользовательских модов.

Дополнительно нужны: immutable IDs/versions, lockfile кампании и мира, путь обновления и rollback, CDN-подписи, ограничение параллелизма, докачка после обрыва, backoff, защита от разархивационной бомбы и path traversal, телеметрия трафика, контроль RAM/GPU.

## 8. Критерии приёмки после разрешённого старта

- Игрок с пустой мастерской заходит в тестовый регион и видит корректную безопасную сцену; optional-качество приходит по сети/потребности.
- У игрока нулевой лимит — корректный fallback или понятная просьба разрешить минимальную загрузку.
- Устройство с малым свободным местом не теряет сейвы и pinned-пакеты; загрузка корректно отказывается.
- Один и тот же ресурс, используемый в пяти чанках, скачивается **один раз на версию/hash**, а не пять.
- Переход по 3×3 / 5×5 чанкам не создаёт утечек RAM/GPU/диска; отрицательные координаты работают.
- Чужой игрок не может навязать клиенту произвольный URL/пакет.
- Смена Android ↔ Windows получает соответствующие варианты bundle и не делит несовместимые бинарники.
- Сессионное право на VTT-карту ограничено участником/временем, без выдачи постоянного права собственности.
- Профилирование: p95 frame time, RAM/GPU, временный диск, cache hit, время входа/перехода, трафик мобильных данных, частота fallback, ошибка загрузки. Численные SLO назначить после реальных замеров.
