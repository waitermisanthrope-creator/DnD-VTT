# Аккаунты и синхронизация персонажей

Разработка находится в `feature/cloud-character-sync`. Номер выпуска, `main`, native-оболочки и OTA-манифест не изменяются. Управляемый Supabase Cloud обслуживает Auth и PostgreSQL; собственный сервер и постоянно включённый ПК не нужны. Пока проект Supabase не создан, доступен прежний гостевой режим и тесты с моками.

## Подключение Supabase Cloud

1. Создайте проект в [Supabase](https://supabase.com/dashboard). Для начала можно выбрать Free; проверьте актуальные лимиты и правила приостановки неактивных проектов.
2. Откройте SQL Editor нового проекта и выполните **только** `supabase/migrations/202610130001_characters.sql`. Файлы `tests/fixtures/cloud_auth.sql` и `tests/cloud_rls_test.sql` предназначены для отдельной тестовой БД, не для рабочего проекта. Миграция выполняется один раз; при ошибке транзакция откатывается.
3. В Authentication включите Email/password и подтверждение почты. Установите минимальную длину пароля не менее 8 символов. В Email Templates → Confirm signup и Reset Password добавьте в текст письма код `{{ .Token }}`. Приложение принимает код непосредственно, поэтому возврат из браузера в Electron/WebView не требуется. Для сброса пароля: отправить письмо → ввести код → «Проверить код восстановления» → ввести новый пароль → «Задать новый пароль».
4. Настройте собственный SMTP-провайдер для публичного использования. Встроенный SMTP Supabase ограничивает адресатов и частоту отправки; он не подходит для общей регистрации пользователей. Проверьте доставку писем, срок действия кодов, rate limits и антиспам-настройки. Пароли обрабатывает исключительно Supabase Auth.
5. Скопируйте Project URL (`https://<project-ref>.supabase.co`) и **публичный publishable key**. На каждом устройстве откройте «Аккаунт» → «Подключение к облаку» и сохраните эти два значения. Для будущей сборки можно заполнить `app/cloud_config.js` одинаковыми публичными параметрами. Secret/service_role ключи в приложение не добавляются; клиент отклоняет их. Legacy anon JWT также поддерживается.
6. Для обращения к проекту из облачной среды разработки добавьте точный hostname `<project-ref>.supabase.co` в Internet access среды. На пользовательских Windows/Android-устройствах нужен обычный HTTPS-доступ к этому домену. Секретные переменные среды приложению не требуются. Project URL и ключ не читаются из окружения Node: браузер получает их из настроек или `cloud_config.js`.
7. Войдите в один аккаунт на обоих устройствах. «Создать облачные копии локальных героев» явно переносит гостевых героев. Каждый запуск этой кнопки создаёт новые копии; исходные ID и байты гостевых сохранений остаются на устройстве. Выйдя из аккаунта, вы снова увидите оригиналы. Новые персонажи, созданные во время входа, автоматически попадают в очередь аккаунта.

Для смены аккаунта сначала завершите сетевую игровую сессию. Это предотвращает применение событий старой комнаты к персонажу другого аккаунта. При выходе локальная сессия удаляется даже без сети, а кэш и очередь сохраняются отдельно для владельца. Для полного удаления данных с устройства служит прежний сброс настроек; он не удаляет облачных персонажей.

## Владение сохранениями и архитектура

| Компонент | Ответственность |
| --- | --- |
| `app/app.js` | `allCharacters`, `currentCharacterId`, `currentChar`/`currentCharacter`; нормализация, загрузка, CRUD, JSON-импорт/экспорт и `autoSaveCurrentCharacter()` → `saveAllCharacters()` |
| `character_creation.js`, `character_builder_v2.js`, `character_creation_pergament.js` | Создание и дополнение профиля; сохраняют через общий API, с прямым fallback в основной ключ |
| `Backgrounds.js`, `data/classes/level_up.js`, `data/feats/Feat_widget.js`, `rulesEngine.js` | Предыстория, прогрессия, черты и импорт; общий API либо прямой fallback |
| `Settings.js`, `Settings_debug.js` | Выбор персонажа, резервные копии, сброс, debug-редактирование; debug также пишет совместимый `dnd_characters`, основной источник — `dnd_multi_characters_v2` |
| `3dmap/character_appearance_store.js` | Прямая запись только `appearance3d` в свежий профиль; получатель и аккаунт закрепляются при открытии редактора |
| `3dmap/map_world.js` | Транзакционный commit профиля через `saveAllCharacters()` |
| `network_engine.js`, `network_gameplay.js` | Существующая игровая авторитетность комнаты и перенос боевых изменений в профиль; не заменяются облачной авторизацией |
| `vtt_mobile_session_v67.js`, `vtt_encounter_checkpoint_v68.js` | Локальные слоты/чекпоинты и восстановление; сохраняют восстановленный профиль через основной API. Сами комнаты, журналы и локальные слоты не являются новым облачным сервисом |
| `cloud_sync.js` | Supabase REST/Auth, refresh сессии, журнал, очередь, CAS, удаление, конфликты, история и локальные резервные версии |
| `cloud_account.js`, `cloud_account.css` | Общий русский интерфейс аккаунтов с кнопками для сенсорного экрана |

Все прямые записи основного ключа найдены в `app.js`, `character_creation.js`, `character_builder_v2.js`, `Backgrounds.js`, `data/classes/level_up.js`, `Settings_debug.js`, `3dmap/character_appearance_store.js`; восстановление резервной копии записывает ключи динамически в `Settings.js`. Модуль синхронизации загружается до старых скриптов и перехватывает `Storage.prototype.setItem/removeItem` только для основного списка своего localStorage. Таким образом, существующие вызовы сохранения из инвентаря, заклинаний, здоровья, навыков, ресурсов, торговли, ремёсел, компаньонов, призывов и сетевой игры проходят через одну точку. `clear()` означает локальный сброс, а не массовое облачное удаление.

Полный список существующих файлов, вызывающих общий API сохранения, зафиксирован в `docs/CLOUD_SAVE_CALLERS.txt`; его можно обновить поиском `rg -l '\b(saveAllCharacters|autoSaveCurrentCharacter)\b' app --glob '*.js'`. Это карта маршрутов записи, а не перечень всех функций, меняющих отдельные игровые поля.

Профиль передаётся целиком как JSONB, включая неизвестные дополнительные поля, инвентарь, классы, деньги, заклинания и `appearance3d`; вручную дублировать игровую модель не нужно. UUID облачной записи хранится отдельно от старого локального ID. На другом устройстве локальным ID становится облачный UUID. `schema_version`, `revision`, `owner_id`, `updated_at`, `deleted` — метаданные БД. Стандартные GLB, текстуры и медиа не загружаются; ссылки и параметры внешности используют локальные ассеты. Для одинакового изображения нужны одинаковые версии ассетов на обоих устройствах.

## Сохранность данных

- `dnd_multi_characters_v2` остаётся форматом активного локального списка, включая поддерживаемую оболочку `{characters:[...]}`. Гостевые данные и кэши аккаунтов раздельно сохраняются в `dnd_cloud_journal_v1`, с пространством имён Project URL + owner UUID.
- Локальная запись подтверждается раньше отправки. Очередь переживает перезапуск, отсутствие интернета и потерю ответа. Запрос содержит неизменяемый UUID операции; durable receipt исключает повторное применение уже выполненного запроса. Изменения, пришедшие во время отправки, остаются следующей записью в очереди.
- Отправка объединяет частые изменения с задержкой 1 секунду. Автоматические сетевые повторы имеют экспоненциальную паузу до 60 секунд и jitter, таймаут запроса — 15 секунд. Ошибки авторизации/конфигурации останавливают повторы до повторного входа/явной попытки. После восстановления сети очередь запускается автоматически. Обновление списка при активной сессии — раз в 30 секунд и при возврате приложения в фокус.
- SQL RPC атомарно проверяет ожидаемую ревизию. Прямые INSERT/UPDATE/DELETE для клиента запрещены. RLS разрешает читать только строки текущего `auth.uid()`; историю другого владельца также нельзя получить по ID. Гости не читают таблицы и не вызывают RPC.
- При конфликте локальная запись не заменяется. Можно явно оставить устройство, выбрать облако или сохранить локальную отдельной копией. Версия до выбора остаётся в локальном архиве, доступном для восстановления копией. Обновление открытого листа тоже требует явного выбора, чтобы не затереть его несохранённое состояние.
- Удаление — CAS tombstone, не исчезновение строки. Устаревший клиент не воскрешает запись автоматически. Удалённый профиль можно восстановить из истории или создать отдельную копию сохранённого локального профиля, в том числе офлайн.
- Сервер хранит последние 30 ревизий каждого профиля. Восстановление создаёт новую ревизию через тот же CAS. Receipt хранит только метаданные, чтобы не дублировать все старые JSON-профили без ограничения.
- Токены сессии не входят в резервные копии приложения или Storage Inspector. Восстановление общей резервной копии возвращает локальный гостевой режим; для облачной очереди нужно заново войти. Пароль не записывается в localStorage, профили, журнал или диагностические логи.

Максимальный размер JSON-профиля для RPC — 1 MiB. При переполнении localStorage запись сообщает ошибку; не удаляйте исходные данные, сначала экспортируйте текущих героев. Журнал и локальные архивы занимают дополнительное место. Несколько одновременно открытых вкладок одной браузерной установки не входят в проверенный сценарий; основная цель — отдельные Windows/Android-приложения.

## Проверки и среда разработки

Существующий checkout уже изолирован задачей; новый worktree не нужен. Node 24 и Python доступны. Electron-зависимости устанавливаются без изменения package.json и без создания lockfile: в исходном репозитории lockfile отсутствовал.

```bash
cd /workspace/DnD-VTT
NODE_USE_ENV_PROXY=1 electron_config_cache=/workspace/.electron-cache npm install --package-lock=false --no-audit --no-fund --cache /workspace/.npm-cache
npm run desktop:prepare
node tests/cloud_sync_test.cjs
node tests/character_appearance_store_test.js
npm run desktop:check
```

Для браузерной разработки запустите `python3 -m http.server 8000 --bind 127.0.0.1 --directory /workspace/DnD-VTT`; это локальный сервер статических файлов для проверки, а не сервер авторизации. В onboarding не создаётся публичное превью. Для графического Electron используйте `npm run desktop:dev` на машине с подходящей графической средой и sandbox; Windows packaging остаётся `npm run desktop:build:win` с `--publish never` из существующего скрипта.

Полноценный браузерный тест использует установленный вне репозитория playwright-core и Chromium:

```bash
PLAYWRIGHT_MODULE=/workspace/cloud-tools/node_modules/playwright-core BROWSER_EXECUTABLE=/usr/bin/chromium node tools/check_cloud_account_browser.cjs
```

SQL проверяется в отдельной локальной PostgreSQL 17 БД, создаваемой и удаляемой тестовым скриптом. Запущенный локальный тестовый PostgreSQL в этой среде слушает 127.0.0.1:5433; он не нужен конечным пользователям:

```bash
bash tools/test_cloud_sql.sh
```

`PG_BIN`, `PGHOST`, `PGPORT` позволяют выбрать собственную **тестовую** установку PostgreSQL. Фикстура Auth эмулирует только UID и роли; реальные пароли/SMTP/сессии Supabase она не проверяет.

На момент подготовки проверены: 15 сценариев CloudSync с моками; фактический PostgreSQL CAS/RLS/история и конкурентная запись через два независимых соединения; полный Chromium-сценарий с двумя независимыми профилями, узким экраном, 3D-параметрами, конфликтом, перезагрузкой и безопасным экспортом; существующие тесты внешности, создания персонажей, V744/V746/V748 сохранений/авторитетности/боёв, V70 диагностики и Electron OTA-контракта. Проверка синтаксиса охватила 232 JS-файла приложения до последних дополнений; изменённые файлы проверены повторно. Все script src в index.html существуют.

Общий старый regression runner начат, но остановлен после группы длительных 3D-тестов; полный набор не объявляется пройденным. Исторические root-relative тесты нужно запускать через совместимый preload общего runner, а не напрямую из tests/. Их исходники не менялись.

**Не проверено:** настоящая регистрация/SMTP Supabase, реальная RLS через облачный REST, сборка и запуск на Windows, физический Android, сравнение отрисовки 3D на двух платформах и восстановление опубликованного snapshot в новой задаче. В текущей Linux-среде Electron-бинарник и webroot подготовлены, Node-режим Electron работает; графический запуск остановлен требованием sandbox helper. Native-оболочки и обновления не изменены.

После создания проекта выполните живой QA: два тестовых аккаунта и запрет доступа к чужому UUID; подтверждение почты и восстановление пароля; один общий аккаунт на Windows/Android, перенос героя с инвентарём/ресурсами/внешностью; изменения в обе стороны; офлайн-изменение и завершение процесса; одновременные изменения и все способы разрешения; удаление на одном устройстве со старой копией на другом; восстановление ревизии; выход/повторный вход; одинаковая внешность при одинаковых ассетах. Только после этих проверок интеграцию можно считать проверенной для выпуска.

Справка: [Supabase Auth](https://supabase.com/docs/guides/auth), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [API keys](https://supabase.com/docs/guides/api/api-keys).

## Тестовые сборки Windows и Android

По запросу владельца подготовлены Windows Portable x64 и отдельный Android debug APK. Исходные native-файлы, номера версий, production signing и OTA-манифест не изменены. Форма входа принимает уже существующий пароль аккаунта; ограничение 8 символов применяется к новой регистрации и смене пароля. Браузерный тест проверяет вход с шестисимвольным паролем тестового аккаунта.

Android собирается с runtime-override из `tools/cloud_test.init.gradle`: ID `com.dndvtt.pocketvtt.cloudtest`, отдельный debug-ключ и вывод вне checkout. APK устанавливается рядом с обычным приложением и имеет собственное хранилище. В локальном списке тестового приложения старых героев сначала не будет: войдите в тот же аккаунт, чтобы скачать облачных героев, или экспортируйте JSON из обычного приложения и импортируйте его в тестовую копию. Ярлык может иметь обычное название приложения; после установки используйте кнопку «Открыть» установщика, чтобы открыть именно новую копию.

Windows Portable запускается без установки и использует обычный профиль существующей Windows-оболочки. Гостевые сохранения остаются доступны при выходе из аккаунта. EXE является неподписанной тестовой сборкой; icon/resource editing пропущен Linux build override, Windows runtime и renderer сохранены.

Инструменты: Gradle 9.6.0, OpenJDK 21 с javac, Android SDK 36 / build-tools 36.0.0; пути находятся в `/workspace/cloud-tools`. Архив Gradle проверен по официальному SHA-256, Android command-line tools — по checksum официального repository XML, JDK — из подписанных метаданных Debian. Для обновлённой сборки в этой среде:

```bash
bash tools/build_cloud_tests.sh
```

Артефакты находятся в `dist/cloud-test`, рядом создаётся `SHA256SUMS.txt`. APK проверен `apksigner verify`, идентификатор подтверждён через aapt. Содержимое account/config/sync/appearance и HTML сравнивается с текущими исходниками в APK и Windows ASAR. Это проверяет сборку и упаковку, но не запуск на реальном Windows/Android и не авторизованную синхронизацию живого аккаунта.

Для проверки: запустите каждую тестовую сборку → «☁ Аккаунт» → введите почту и пароль созданного подтверждённого пользователя → «Войти». На Windows перенесите гостевого героя кнопкой облачных копий, дождитесь «Синхронизировано», затем войдите тем же аккаунтом в Android-копии и проверьте героя. Пароль вводится только в приложении; агенту его передавать не нужно. Публичный Project URL и ключ уже включены в оба пакета. Самостоятельную регистрацию и восстановление письмами проверьте после настройки SMTP; созданный вручную подтверждённый пользователь входит без этого этапа.

## Обновления тестовых приложений из приложения

Облачные тестовые сборки используют `updates/cloud-test.json` в ветке
`feature/cloud-character-sync`. Обычный `updates/stable.json` не меняется.
При недоступности тестового источника переход на stable запрещён: приложение
продолжает работать с установленными файлами.

Пользователь один раз устанавливает сборку с этим каналом, затем использует
«Настройки → Обновление приложения → Проверить и обновить». Проверка также
происходит после стартовой заставки. Почта и пароль от облака для обновления
не нужны. Обновляется HTML/JS и содержимое приложения; изменение Java-кода
Android или Electron требует нового APK/EXE.

Для следующего тестового обновления разработчик:

1. Увеличивает `APP_VERSION` в `app/update_manager_v2.js` и проверяет изменения.
2. Делает коммит исходников; получает SHA через `git rev-parse HEAD`.
3. Запускает генератор с `--base-url https://raw.githubusercontent.com/waitermisanthrope-creator/DnD-VTT/<SHA>`
   `--version <APP_VERSION> --min-app-version 74.00.62 --channel beta`
   `--output updates/cloud-test.json`.
4. Проверяет размеры и SHA-256 файлов, коммитит манифест и отправляет оба
   коммита в тестовую ветку. Файлы закреплены за неизменяемым SHA, а указатель
