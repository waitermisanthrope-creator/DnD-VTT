Requires existing migrations 001–003, then `supabase/migrations/202610210004_authenticated_chat.sql` and `supabase/enable_chat_retention.sql` through trusted SQL Editor. Do not rerun older migrations. Confirm cron job dnd-vtt-chat-expiry actually succeeds after scheduling.

Only signed-in users see the home Chat entry; server independently checks JWT identity and current platform ban. Current mute now blocks chat sends too, while allowing reads. One global room, last 100 nonexpired messages, poll every ten seconds only while chat is open, 1,000 characters/message, ten sends/minute/account. No anonymous read/write, no table access and no client purge grant. UUID send retry is idempotent while the row exists; changed payload/other author under same UUID rejected. No offline message outbox or local history file. Logout clears memory. Plain GUI labels disable markup. Current author display is UUID, not private email. Full-text search, older-message pagination and push notifications are not implemented.

Server returns only messages newer than one hour and expiry timestamps; client hides expired received rows too. Purge runs every minute and physically removes rows older than one hour. Thus visible history is limited to one hour, normal physical cleanup lag is up to a scheduling interval; outages can delay purge. Do not promise exact-second physical erasure or deletion from provider backups/WAL, Auth/gateway logs or screenshots. No raw message bodies are copied into the 24-hour administrative audit. Chat scheduler execution metadata follows the existing 24-hour job-history policy and contains only command/result counts. Provider retention must be configured separately.

Local SQL tests execute real PostgreSQL WASM with simulated Auth claims: anon/ban/mute denial, rate/length limits, retry/collision, no direct reads or purge, expired read cutoff and expired-only deletion, no chat body in audit.
